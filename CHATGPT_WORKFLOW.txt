SMART SCHEDULE — CHATGPT/CODEX UPDATE INSTRUCTIONS

SECURE CONNECTOR WORKFLOW

When the user says that an update is waiting in Firebase or asks to use Smart Schedule without attaching JSON:

1. Use list_pending_schedule_updates.
2. Generate one new UUID claimId for this processing run. Claim the intended submission with claim_schedule_update before editing the repository. Reuse that same claimId only when retrying this exact claim; a different claimId is a different worker and must not take an active lease.
3. Treat the returned payload exactly like a changes-only smart-schedule-update file.
4. Read data/schedule.json and data/schedule-profile.json from ITLegend-co/scheduling-system before applying anything.
5. Apply only the requested changes. Preserve all unmentioned events and profile entries. Ignore Event-Based Tasks unless the user explicitly reverses that instruction.
6. Replace data/update-release.json with a receipt containing only the submission(s) handled by this release. Copy the exact claimId and every requestId returned by claim_schedule_update:

   {
     "format": "smart-schedule-release-receipt",
     "version": 1,
     "preparedAt": "CURRENT_ISO_DATE_TIME",
     "submissions": [
       {
         "submissionId": "EXACT_CLAIMED_SUBMISSION_ID",
         "claimId": "EXACT_CLAIM_UUID",
         "requestIds": ["EXACT_REQUEST_ID"]
       }
     ]
   }

7. Validate the schedule, profile, PWA, and request handling; generate the calendar feed; then commit the intended changes directly to main.
8. Never mark a Firebase request applied yourself. Only the post-deployment GitHub Actions job may change processing to applied after Firebase synchronization and GitHub Pages deployment both succeed.
9. If processing cannot be completed safely, call release_schedule_update with the same claimId and a short reason. Do not leave a knowingly abandoned request claimed.

The browser keeps submitted cards until it observes applied with the exact same request IDs. A build, synchronization, or deployment failure must not clear them.

JSON FILE FALLBACK

If the user attaches a smart-schedule-update JSON file instead, apply it using the same rules below. Leave data/update-release.json with an empty submissions array unless that update was actually claimed through the secure connector. A clear plain-text scheduling request is still accepted as a fallback.

JSON UPDATE FILE RULES

- Accept format: "smart-schedule-update" with version: 1.
- Treat instructions.mode: "changes-only" as mandatory.
- Preserve every unmentioned event. Never replace the full schedule with the update file.
- Apply each changes[] item according to action: add, update, complete, or remove.
- For update, complete, or remove, match existingEventId first. If it is missing, match using the exact title and date; ask if the match is ambiguous.
- Use autoScheduleMissingTimes and createDeadlineWhenMissing from the file when arranging incomplete items.
- Ignore requestId when generating the final schedule event ID; create or preserve a stable event ID instead.
- Ignore Event-Based Tasks.

MASTER PROFILE RULES

- data/schedule-profile.json is the structured replacement for help update schedule.txt and is displayed by update.html.
- Treat smart-schedule-profile as background context, not as a request to replace data/schedule.json.
- A smart-schedule-update file contains the user's requested changes. Apply it to the existing schedule and preserve unmentioned events.
- When a request changes long-term work rules, ongoing tasks, meetings, or personal preferences, update the matching profile entry as well as any affected schedule events.

ARRANGEMENT RULES FOR CHATGPT

- Use the Asia/Kuala_Lumpur timezone unless the request says otherwise.
- Treat existing confirmed events as fixed.
- Keep the configured buffer between separate commitments when possible.
- Place flexible work inside the configured workdays and working hours.
- Schedule urgent and high-priority items before lower-priority flexible work.
- Respect deadlines, preferred times, travel time, and dates to avoid.
- Never create an accidental overlap. Use allowOverlap: true only when explicitly intended.
- If no suitable slot exists, do not guess. Record the issue in the GitHub reply and ask for an alternative.
- Give each new event a stable lowercase ID, for example: prepare-monthly-report-2026-08-18.
- Use ISO date-times with the Malaysia offset, for example: 2026-08-18T09:00:00+08:00.
- For all-day events, use YYYY-MM-DD and set allDay to true.
- Update meta.lastUpdated every time the schedule changes.
- Run: node scripts/validate-schedule.mjs
- Run: node scripts/validate-profile.mjs
- Run: node scripts/test-update-requests.mjs
- Run: node scripts/validate-pwa.mjs
- Run: node scripts/generate-ics.mjs data/schedule.json schedule.ics
- Commit only the intended scheduling changes.
